Reading the numbers side by side: Bitwarden's much smaller request volume per minute (its handlers do real crypto/DB work) still produced two orders of magnitude more coverage edges and unique crashes than eShopOnWeb — it's a larger, more complex codebase, and the point of coverage guidance is exactly to spend the budget where the surface actually is. eShopOnWeb's crash count trending down at longer budgets is expected: the sequence engine and crash-boost logic exhaust the small number of distinct bugs a ~30-endpoint API has, then keep refining reproducibility rather than finding new ones.

Correction (2026-07-25): a POST /settings/domains SSRF row previously shown here has been removed — it was a false positive, and the oracle bug that caused it is now fixed. That endpoint stores an arbitrary user-submitted domain list and echoes it back unchanged (SettingsController → DomainsResponseModel) — there is no outbound HTTP fetch anywhere in that code path. The old ssrf_metadata_reflected check flagged it anyway because two of its four body markers were themselves literal substrings of the SSRF payloads being sent, so a plain echo of our own input satisfied the check. Root-caused and fixed in void/go/identity.go::exploitationSignals after a fresh 1-hour campaign failed to reproduce this finding — see benchmarks/reports/BITWARDEN_1HOUR_REPORT.md for the investigation.
