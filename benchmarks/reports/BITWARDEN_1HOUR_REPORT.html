Reading the numbers: 2,641 "unique crashes" is not 2,641 bugs

The engine's per-payload dedup produces 2,641 distinct crash signatures. Root-cause clustering collapses those into 73 distinct root causes — and even that number is dominated by one pattern: a single cluster (a routing/authorization assertion, detailed below) accounts for 2,054 of the 2,641 raw signatures (78%) on its own. This report's counts use the 73 distinct-root-cause number throughout.

Coverage edges over the hour (295,481 final, 3,293 instrumented types)

Methodology

  • Target: fresh git clone of bitwarden/server (2026-07-25) — now on .NET 10 (was .NET 8 in this project's earlier runs). 22 projects instrumented, --instrument-all-user-code, --cmplog active.
  • Data population: Bitwarden's own util/SeederApi — 3 users, 1 organization with a confirmed owner, 1 folder, 3 login ciphers, 1 org collection. Real encryption via Bitwarden's own Rust SDK.
  • Auth: 4 identities — 3 real users via API-key client_credentials grant, plus an unauthenticated guest, weighted scheduling.
  • Dictionary: dict.custom.json (the new custom-dictionary convention) seeded with real IDs/keys discovered during seeding.
  • Run: -profile security -seed 42 -time-budget 60, HTTP coverage mode.

Findings — triaged by how real and how critical each one actually is

Every classification below is the tool's own honest-triage label. This section exists specifically to separate "the fuzzer flagged something" from "this is a real, exploitable bug" — in a run this size, most flagged signals are the former.

Tier 1 — Needs manual verification, and worth doing

likely_vuln_high Cross-identity device lookup by identifier

GET /devices/identifier/{id} · POST /devices/{id}/retrieve-keys · 9 flagged instances · access_control: true

The access-control oracle registered a device under one identity, then successfully replayed the same lookup under a different identity and got a byte-identical response back (the strong bola_identical_cross_identity_response variant, not just "suspected"). Caveat, stated honestly: every instance observed had encryptedUserKey/encryptedPublicKey both null — the identifier used was fuzzer-generated garbage, so no device had real key material attached yet. The access-control gap looks real; this run didn't prove it leaks anything sensitive. Manually repeat against a device with real key material to confirm impact.

Tier 2 — Flagged by the tool, debunked on inspection

debunked Public-key cross-identity access — by design

GET /users/{userId}/public-key · 2 instances

A user's public key exists specifically so other users can fetch it for end-to-end key exchange. Not a vulnerability — a documented gap in the oracle itself (no way yet to know an endpoint is intentionally cross-identity-readable).

debunked sqli_time_based on rejected requests

DELETE /accounts · POST /accounts/verify-password · POST /webauthn/attestation-options · 3 instances

All three fired on HTTP 400 responses ("User verification failed" / "Invalid password") — the request was rejected before doing anything SQL-adjacent, and none were repro-verified. Timing noise from concurrency contention under load, not SQL injection. Same conclusion this project reached on the same finding shape in an earlier campaign.

Tier 4 — Systemic pattern, real, low severity individually

Unvalidated GUID/Base64 route parameters — ~20 endpoints, one root cause repeated

Unrecognized Guid format, Byte array for Guid must be exactly 16 bytes long, Illegal base64url string! — Devices, Ciphers, Folders, Sends, Organizations, and SelfHostedOrganizationLicenses controllers all parse a route/body value as a GUID or base64 string without validating shape first. Not independently exploitable, but the same input-validation mistake made independently in ~20 places — a real, actionable ticket.

The 78%-of-all-crashes cluster is a framework-internal routing assertion

A route decorated with '[Authorize<IOrganizationRequirement>]' must include a route value named 'orgId' or 'organizationId'... — 2,054 of 2,641 raw crash signatures, one cluster. Fires when a mutated URL matches a controller/action's route template without the route-value name the authorization attribute's own reflection check expects. Real and externally triggerable, but its security relevance is limited to "causes a 500 instead of a clean 4xx" — hence needs_review, not likely_vuln.

Toolchain bugs found along the way (not Bitwarden bugs)

Standing up util/SeederApi (not previously used by this project) surfaced two real bugs in its own Dockerfile/csproj:

  1. util/SeederApi/Dockerfile sets CARGO_TARGET_DIR=/tmp/cargo_target before building its Rust crypto SDK, silently breaking RustSdk.csproj's hardcoded Content Include glob — the published image ships with no native crypto library at all.
  2. Once fixed, RustSdk.csproj has no linux-arm64 entry (only x64/osx-arm64/windows-x64) — building on an arm64 Docker host produces a .so that never gets linked into the runtime path. The Dockerfile's --platform=$BUILDPLATFORM pattern means Rust always targets the builder's native arch since no --target flag is ever passed to cargo build.

Both fixed locally for this run; not upstreamed (out of scope), reported here for completeness.

Caveats, stated plainly

  • Development-mode stack traces inflate what's visible here — 510 of this run's findings carry dev-mode exception detail a production self-hosted deployment wouldn't expose.
  • Placeholder billing/installation credentials cause several Tier 3 findings — not real Bitwarden defects.
  • Single local test environment, not bitwarden.com or any production deployment.
  • Only 3 seeded users / 1 org / 3 ciphers — a broader seed (more users, populated device key material) would likely surface more Tier-1-quality findings.
