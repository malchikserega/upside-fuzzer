\begin{abstract}
% ============================================================
REST APIs are a primary attack surface in modern microservice architectures, yet automated security testing of such APIs remains exceptionally challenging. Specification-based black-box fuzzers such as RESTler~\cite{restler_icse19} generate structurally valid HTTP request sequences from OpenAPI documents. However, they rely on generic, type-level value dictionaries that routinely fail to satisfy the semantic validation constraints enforced by backend business logic---constraints such as bounded integer ranges, regular-expression-validated strings, or valid domain enumerations. As a result, the vast majority of mutated payloads are rejected at the validation layer, leaving deep code paths unexplored and high-severity bugs undiscovered.

We present \textbf{UpsideFuzz}, an end-to-end greybox API fuzzing framework for .NET applications that eliminates this semantic gap through three complementary contributions. First, we introduce \textit{Semantic Source Extraction} (SSE), a static analysis pass that parses C\# source code to recover precise validation constraints from Data Annotation attributes (e.g., \texttt{[Range]}, \texttt{[StringLength]}, \texttt{[RegularExpression]}) and FluentValidation rule chains, and automatically synthesizes boundary-focused seed values for RESTler's mutation dictionaries. Second, we describe an automated instrumentation pipeline that instruments arbitrary .NET Dockerized applications using SharpFuzz~\cite{sharpfuzz} IL-level bytecode injection, enabling edge-coverage measurement via shared-memory bitmaps without modifying application deployment topology. Third, we implement \textit{Void}, a high-concurrency Go-based execution engine that drives the coverage-guided evolutionary loop: it replays RESTler-generated request sequences, collects per-request edge-coverage deltas from the .NET runtime via shared memory, and evolves a seed corpus using an AFL-style bitmap novelty criterion.

We evaluate UpsideFuzz on three open-source .NET applications. Compared to the RESTler baseline, UpsideFuzz achieves between $+127\%$ and $+169\%$ more unique edges covered within a 24-hour campaign, and reduces the median time-to-first-crash from several hours to under one hour.
\end{abstract}

\section{Introduction}
% ============================================================
The widespread adoption of microservice architectures has made REST APIs a critical component and a corresponding attack surface of modern enterprise software. Security testing of REST APIs presents challenges distinct from those in binary fuzzing: (i)~inputs must conform to complex, stateful HTTP protocols and JSON schemas to reach application logic; (ii)~API endpoints typically enforce multi-layered semantic validation before any interesting business logic is exercised; and (iii)~the testing target is a remote, distributed black box.

Stateful black-box fuzzers, exemplified by RESTler~\cite{restler_icse19}, address challenge~(i) by inferring producer-consumer dependencies from an OpenAPI specification and building a grammar that generates syntactically well-formed, stateful request sequences. RESTler's value dictionaries, however, consist of a small, fixed set of type-level tokens (e.g., \texttt{"fuzzstring"}, \texttt{0}), making it structurally incapable of satisfying challenge~(ii). As Godefroid et al.\ later noted~\cite{restler_fse20}, the data payloads embedded in REST API requests are a crucial and largely unexplored testing dimension. Their follow-up work on \textit{Intelligent REST API Data Fuzzing} focuses on schema-level structural mutations but relies solely on information already present in the Swagger specification; source-code validation semantics remain outside its scope.

Coverage-guided greybox fuzzers such as AFL and, for .NET, SharpFuzz~\cite{sharpfuzz} address challenge~(iii) by measuring edge coverage via shared-memory instrumentation and using a bitmap novelty criterion to evolve the seed corpus. Applied to structured network protocols, however, bit-level mutations corrupt the HTTP envelope and JSON syntax, causing payloads to be immediately rejected at the web server routing layer---far upstream of any application logic.

\textbf{Our position.} These two paradigms are complementary: specification-based fuzzers excel at navigating API state machines but are semantically blind; coverage-guided fuzzers excel at exploration but are structurally blind. UpsideFuzz bridges this gap for .NET applications by combining (a)~static recovery of application-level validation semantics directly from C\# source code, (b)~automated SharpFuzz IL instrumentation of the target server, and (c)~a coverage-guided evolutionary engine that operates at the granularity of structured HTTP requests.

\textbf{Contributions.} This paper makes the following contributions:
\begin{itemize}
    \item \textbf{Semantic Source Extraction (SSE):} A static analysis technique for C\# that recovers field-level validation constraints from Data Annotation attributes and FluentValidation rules and synthesizes boundary-focused dictionary values for RESTler's grammar without modifying the RESTler compiler (\S\ref{sec:sse}).
    \item \textbf{Multipart Grammar Injection:} An automated pass that detects \texttt{multipart/form-data} endpoints in OpenAPI specifications and injects syntactically correct, RESTler-native seed request templates, enabling fuzzing of file-upload endpoints that RESTler's compiler cannot handle out-of-the-box (\S\ref{sec:multipart}).
    \item \textbf{Automated IL Instrumentation Pipeline:} A reproducible pipeline that instruments arbitrary .NET Docker images via SharpFuzz without requiring manual harness development, by patching the application Dockerfile at build time (\S\ref{sec:instrumentation}).
    \item \textbf{Void Execution Engine:} A highly concurrent Go-based runner that drives the greybox evolutionary loop over RESTler-compiled grammars, collecting edge-coverage feedback from the instrumented .NET process via shared memory (\S\ref{sec:void}).
    \item \textbf{Empirical Evaluation:} A 24-hour comparative study on three open-source .NET applications demonstrating significant improvements in edge coverage and crash discovery over the RESTler black-box baseline (\S\ref{sec:eval}).
\end{itemize}

\section{Background and Related Work}
\label{sec:background}
% ============================================================

\subsection{Coverage-Guided Greybox Fuzzing}
The American Fuzzy Lop (AFL) fuzzer established the paradigm of coverage-guided greybox fuzzing~\cite{afl}: an instrumentation pass injects counters at every branch edge; a shared-memory bitmap records which edges have been hit during an execution; and a seed corpus is grown by retaining any input that produces a novel bitmap entry. AFL-style coverage-guided fuzzing has proven highly effective for binary targets. SharpFuzz~\cite{sharpfuzz} adapts this paradigm to .NET by post-processing compiled Intermediate Language (IL) bytecodes with a binary rewriter that inserts edge-counter updates, requiring no source modifications.

\subsection{Specification-Based API Fuzzing}
RESTler~\cite{restler_icse19} is the first stateful REST API fuzzer. Given an OpenAPI specification, RESTler performs a lightweight static analysis to identify producer-consumer dependencies between request types (i.e., resources created by one request and consumed as input by another). It then generates and executes test sequences using a grammar that encodes these dependencies, guided dynamically by HTTP response codes. RESTler's grammar distinguishes \emph{static} tokens (constants copied from the specification) from \emph{fuzzable} tokens (type-annotated placeholders replaced at execution time by dictionary values). The default dictionary contains a small number of type-generic values; domain-specific values must be supplied manually.

\subsection{Intelligent API Data Fuzzing}
Godefroid et al.~\cite{restler_fse20} study a complementary dimension: intelligently fuzzing the \emph{data payloads} embedded in REST API request bodies. They propose and evaluate a range of structural schema fuzzing rules (e.g., type substitution, field deletion, value replication) and two concrete-value generation techniques: extracting values from specification examples, and learning values on-the-fly from prior service responses. Their work confirms that type-generic random mutation is ineffective for structured JSON and that domain-specific values significantly increase bug-discovery rates. UpsideFuzz extends this insight to the .NET ecosystem by automatically recovering domain-specific constraints from \emph{server-side application source code}---a dimension not considered in prior work.

\subsection{Other Related Tools}
EvoMaster~\cite{evomaster} uses an evolutionary algorithm guided by white-box instrumentation (via bytecode transformation for JVM-based services) to generate REST API test cases. Unlike UpsideFuzz, EvoMaster targets JVM languages, requires a heavyweight agent attached to the process, and does not leverage source-level validation annotations. WuppieFuzz~\cite{wuppiefuzz} is a recent LibAFL-based framework supporting black-box, grey-box, and white-box REST API fuzzing across multiple server-side languages, but does not perform source-level semantic extraction. Dredd~\cite{dredd}, APIFuzzer~\cite{apifuzzer}, and schemathesis~\cite{schemathesis} are generation-based tools that rely exclusively on the OpenAPI specification; they do not measure code coverage and are therefore purely black-box. Our work is the first to recover validation semantics from C\# source code and couple them with a native coverage-guided loop specifically for .NET REST services.

\label{sec:arch}
% ============================================================

UpsideFuzz consists of four loosely coupled components executed in two phases: an offline \emph{preparation phase} (instrumentation and grammar compilation) and an online \emph{fuzzing phase} (execution and corpus evolution). Figure~\ref{fig:arch} illustrates the end-to-end pipeline.

\begin{figure}[htbp]
%\centerline{\includegraphics[width=\columnwidth]{figures/architecture.pdf}}
\caption{UpsideFuzz end-to-end architecture. Solid arrows denote offline preparation; dashed arrows denote the online fuzzing loop.}

\textbf{Preparation phase.} Given a target .NET application repository and an OpenAPI specification, the user runs:
\begin{enumerate}
    \item \texttt{fuzz-prep-multi.py}: instruments the application image (Section~\ref{sec:instrumentation});
    \item \texttt{compile-grammar.sh}: invokes the RESTler compiler to produce a raw grammar, then calls the SSE enhancer (Section~\ref{sec:sse}) to augment it.
\end{enumerate}

\textbf{Fuzzing phase.} The Void execution engine (Section~\ref{sec:void}) is started alongside the instrumented application container. Void replays RESTler grammar sequences, collects coverage bitmaps from the instrumented process, and evolves its seed corpus.

\section{Automated Instrumentation Pipeline}
\label{sec:instrumentation}
% ============================================================

To obtain edge-coverage feedback without altering the application's runtime topology or requiring custom test harnesses, UpsideFuzz injects SharpFuzz instrumentation at Docker image build time. Our preparation script \texttt{fuzz-prep-multi.py} performs the following steps automatically:

\begin{enumerate}
    \item \textbf{Clone and amend.} The script clones the target repository and inserts a SharpFuzz installation step into the \texttt{Dockerfile} ENTRYPOINT layer, pulling the \texttt{SharpFuzz.Instrumentation} NuGet package.
    \item \textbf{IL rewriting.} During the amended image build, the SharpFuzz instrumentor rewrites all first-party \texttt{.dll} assemblies produced by the .NET SDK. For each method body, it inserts a XOR-based edge counter update before every branch target:
        \begin{equation}
          \text{bitmap}[(\text{prev\_loc} \oplus \text{cur\_loc}) \gg 1]\ \text{+=}\ 1
          \label{eq:shm}
        \end{equation}
        where \texttt{prev\_loc} and \texttt{cur\_loc} are compile-time-assigned random 16-bit identifiers for each basic block, following the AFL SHM protocol~\cite{afl}. This yields a 65,536-entry byte array in a POSIX shared-memory segment.
    \item \textbf{Coverage endpoint.} The script optionally patches the application's \texttt{Program.cs} to expose an in-process HTTP endpoint that serializes the shared-memory bitmap over HTTP, enabling coverage polling without inter-process memory mapping in Docker bridge-network mode.
    \item \textbf{Docker Compose update.} The \texttt{docker-compose.yml} is amended to expose the coverage endpoint and to configure the shared-memory segment (\texttt{/dev/shm}).
\end{enumerate}

The entire preparation completes in the time required for a \texttt{docker build} cycle (typically 3--8 minutes for medium-size applications), with zero manual harness code.

\section{Semantic Source Extraction}
\label{sec:sse}
% ============================================================

\subsection{Motivation}
When RESTler replaces a fuzzable token typed as \texttt{string}, it substitutes a value from its dictionary, typically containing only a generic placeholder such as \texttt{"fuzzstring"} or \texttt{"[FUZZ]"}. A backend validator enforcing \texttt{[StringLength(8, MinimumLength=4)]} will immediately return HTTP 400 on this input, and RESTler's dynamic feedback mechanism will record the sequence as unproductive and deprioritize it. The fuzzer thus never reaches the code paths that process valid strings. Our Semantic Source Extraction (SSE) pass addresses this by automatically populating dictionaries with constraint-aware boundary values derived from the application's own validation logic.

\subsection{Pipeline Overview}
SSE operates in two sub-passes: (i)~an OpenAPI extraction pass that reads the Swagger specification to collect declared constraints such as \texttt{minLength}, \texttt{maxLength}, \texttt{minimum}, \texttt{maximum}, \texttt{pattern}, and \texttt{enum}; and (ii)~a source extraction pass that statically scans the C\# source tree to recover constraints that are absent from or more precise than the specification.

\subsection{OpenAPI Constraint Extraction}
The \texttt{OpenAPIExtractor} class performs a recursive traversal of the Swagger schema graph, resolving \texttt{\$ref} pointers and expanding \texttt{allOf}/\texttt{oneOf}/\texttt{anyOf} combinators. For each leaf property, it produces a \texttt{FieldHint} descriptor capturing the field's type, format, declared constraints, and any inline \texttt{example} or \texttt{default} values. Fields of type \texttt{string} with format \texttt{binary} appearing in \texttt{multipart/form-data} operations are tagged as file-upload fields and routed to the multipart injection pass (Section~\ref{sec:multipart}).

\subsection{C\# Source Code Constraint Extraction}
\label{sec:src_extract}
The \texttt{SourceExtractor} class performs a regex-based pass over all \texttt{.cs} files in the target source tree. While full Roslyn-based AST analysis would offer higher precision, we intentionally use regex to avoid introducing a heavyweight .NET SDK dependency into the Python pipeline; in practice, .NET validation attributes follow highly regular syntactic patterns that regex handles reliably.

\textbf{Data Annotation Attributes.} The extractor identifies attribute blocks preceding property or parameter declarations and parses the following attributes (case-insensitive):
\begin{itemize}
    \item \texttt{[StringLength(N)]} and \texttt{[StringLength(N, MinimumLength=M)]}: sets $\textit{max\_length} = N$, $\textit{min\_length} = M$.
    \item \texttt{[MaxLength(N)]}, \texttt{[MinLength(M)]}: sets the corresponding bound.
    \item \texttt{[Range(lo, hi)]}: sets $\textit{minimum} = lo$, $\textit{maximum} = hi$.
    \item \texttt{[RegularExpression("pattern")]}: stores the regex pattern.
    \item \texttt{[Required]}: marks the field as non-nullable.
    \item \texttt{[EmailAddress]}, \texttt{[Url]}: activates format-specific value generators.
\end{itemize}

\textbf{FluentValidation Rules.} For validators that extend \texttt{AbstractValidator<T>}, the extractor scans \texttt{RuleFor(...)} chains and recognizes the following rule methods:
\begin{itemize}
    \item \texttt{.MaximumLength(N)}, \texttt{.MinimumLength(M)}, \texttt{.Length(M,N)}: string length bounds.
    \item \texttt{.InclusiveBetween(lo, hi)}, \texttt{.ExclusiveBetween(lo, hi)}: numeric bounds.
    \item \texttt{.GreaterThan(v)}, \texttt{.LessThan(v)}: one-sided numeric bounds.
    \item \texttt{.Matches("pattern")}: regex pattern.
    \item \texttt{.NotEmpty()}, \texttt{.NotNull()}: required-field marking.
    \item \texttt{.EmailAddress()}, \texttt{.Must(IsUrl)}: format validators.
\end{itemize}
When a constraint is found in both sources, the tighter bound is retained (max of minimums, min of maximums), reflecting conservative worst-case semantics.

\textbf{Enum Resolution.} For each property or parameter whose type resolves to a C\# \texttt{enum}, the extractor locates the enum declaration in the source tree and parses all symbolic members, including their optional explicit integer assignments. Both the symbolic name and its integer equivalent are added to the dictionary, following the observation in~\cite{restler_fse20} that enum-constrained fields require exact value matches to progress past validation.

\subsection{Boundary Value Synthesis}
Given a \texttt{FieldHint} with collected constraints, SSE synthesizes a set of \emph{boundary-focused seed values} designed to probe the frontiers of validation logic. For numeric fields, the synthesizer generates $\{lo-1, lo, hi, hi+1\}$; for string-length-constrained fields, it generates strings of lengths $\{max-1, max, max+1\}$ and $\{min-1, min, min+1\}$ (where $min-1$ produces the empty string if $min \leq 1$). For regex-constrained fields, it generates one matching example string and one known-invalid string. These boundary values are injected into the RESTler dictionary under all known key variants of the field name (camelCase, PascalCase, lowercase), ensuring they are matched regardless of serialization conventions.

An important property of SSE is its \emph{composability}: it does not modify the RESTler grammar structure or its compiler; it only augments the dictionary and appends seed request templates. RESTler's existing dependency-inference and search strategies remain fully intact.

\section{Multipart Grammar Injection}
\label{sec:multipart}
% ============================================================
REST endpoints accepting \texttt{multipart/form-data} bodies (common for file uploads) are poorly supported by RESTler's compiler: the generated grammar emits a single fuzzable token of type \texttt{string} for the entire body, which is syntactically invalid. UpsideFuzz detects all \texttt{multipart/form-data} operations in the OpenAPI specification (flagged during SSE's OpenAPI pass) and generates corrected RESTler-native request templates. Each template encodes the MIME boundary string, per-field Content-Disposition headers, and a binary payload stub (\texttt{fuzz.bin}) for file-typed fields. These templates are appended directly to \texttt{grammar.py} as additional \texttt{Request} objects, enabling the Void engine to exercise file-upload endpoints without any manual configuration.

\section{The Void Execution Engine}
\label{sec:void}
% ============================================================

\subsection{Architecture Overview}
Void is a multi-goroutine HTTP fuzzing engine implemented in Go ($\sim$3,500 lines). Its overall structure follows a producer-consumer pipeline: a \emph{dispatcher goroutine} generates \texttt{WorkItem} structs (each encoding an HTTP method, path, body, headers, mutation name, and seed index), enqueues them into a bounded channel, and a fixed \emph{worker pool} of goroutines concurrently dispatches them over HTTP. Completed \texttt{SendResult} structs are returned via a result channel to a single \emph{result handler} that updates global state without locks.

\subsection{SharpFuzz Instrumentation and Coverage Transport}
\label{sec:coverage_transport}

\textbf{SHM bitmap layout.} The SharpFuzz instrumentor rewrites compiled IL bytecodes at build time, inserting a branch-hit counter at every branch edge. For each edge $(u \to v)$ in the control-flow graph, SharpFuzz assigns a random 16-bit identifier $l_u$ to the source block and updates the shared-memory bitmap as:
\begin{equation}
  \text{shm}\bigl[(l_u \oplus l_v) \gg 1\bigr] \mathrel{+}= 1
  \label{eq:shm_edge}
\end{equation}
where $l_u$ is the block ID of the previous basic block (thread-local), and $l_v$ the ID of the target block. This produces a 65,536-byte POSIX shared-memory region mapping each possible edge index to a hit count, exactly matching the AFL protocol~\cite{afl}.

\textbf{Two coverage transport modes.} The instrumented .NET process exposes the bitmap in two transport modes, selected at startup:

\begin{enumerate}
    \item \textbf{Direct SHM mode} (\texttt{SHMCoverageReader}): Void opens the SHM region as a file under \texttt{/dev/shm}, shared via a Docker volume mount. The reader maintains a local \texttt{seen[65536]} accumulator byte array. On every poll, it scans the SHM buffer and counts bytes that are non-zero in the SHM but zero in \texttt{seen[]}, recording them as new edges:
\begin{lstlisting}
for i, b := range shmBuf {
    if b != 0 && seen[i] == 0 {
        seen[i] = 1; edges++ } }
\end{lstlisting}
    Crucially, the SHM bitmap is \emph{never reset between individual requests} in this mode. The .NET runtime writes cumulatively; Void tracks what it has already observed via \texttt{seen[]}. The bitmap is only zeroed (and \texttt{seen[]} cleared) when global bitmap occupancy exceeds 85\%, indicating that hash collisions have made the novelty signal unreliable.
    \item \textbf{HTTP coverage mode} (\texttt{HTTPCoverageReader}): The patched ASP.NET Core \texttt{Program.cs} exposes three in-process HTTP endpoints---\texttt{/shm/create}, \texttt{/shm/coverage}, \texttt{/shm/reset}---that manage a per-application SHM bitmap. Void calls \texttt{Reset()} before the target request, and \texttt{GetEdges()} after, obtaining a reliable per-request coverage count. This mode is used in Docker bridge-network deployments where Docker volume file sharing is unavailable.
\end{enumerate}

\subsection{Attribution Accuracy: HTTP Mode vs.\ Direct SHM Mode}
\label{sec:attribution}

The two transport modes differ fundamentally in their ability to attribute coverage to specific requests, particularly under concurrent execution (Figure~\ref{fig:attribution}).

\textbf{HTTP mode (exact attribution).} The ASP.NET Core middleware executes synchronously within the request pipeline. The sequence is strictly:
\begin{enumerate}
  \item Middleware intercepts the request, calls \texttt{SharpFuzz.ResetCoverage()}.
  \item The controller executes; SharpFuzz writes branch hits into the SHM bitmap.
  \item Before closing the response, middleware counts the set bytes: \texttt{delta = bitmap.CountNonZero()}.
  \item Delta is written into the \texttt{X-Coverage-Delta} response header.
  \item Void receives the response and records: \emph{this exact} \texttt{(METHOD, path, body)} produced \texttt{delta} new edges.
\end{enumerate}
This attribution is correct even under high concurrency because each HTTP request gets its own middleware invocation; the \texttt{Reset}/\texttt{Count} pair brackets exactly one controller execution.

\textbf{Direct SHM mode (approximate, interval-based attribution).} With many worker goroutines running concurrently, up to \texttt{MaxConcurrency} requests execute in parallel in the .NET process. All write into the same shared bitmap simultaneously. When Void later reads a coverage delta via \texttt{GetEdges()}, it cannot determine which of the concurrent requests triggered the new edges:
\begin{lstlisting}
// After CoverageInterval completions:
delta = GetEdges() - previousEdges
if delta > 0 {
    // Attribute delta to the most recently
    // completed request -- an approximation
    addOrBoostSeed(lastCompletedItem) }
\end{lstlisting}
This heuristic attribution is a deliberate engineering trade-off: direct SHM avoids middleware patching and HTTP round-trips, but produces noisy seed--coverage correlation. The corpus evolution mechanism (Section~\ref{sec:corpus}) remains effective because even approximate attribution preserves the relative ranking of productive vs.\ unproductive endpoints over many observations.

In practice, HTTP mode is preferred when the target application's middleware can be patched (i.e., when \texttt{fuzz-prep-multi.py} succeeds in injecting the coverage shim). Direct SHM is the fallback for third-party applications or Docker configurations that prohibit middleware injection.

\textbf{Void's dual-path result handler} implements the decision transparently:
\begin{lstlisting}
if res.CoverageDelta > 0 {
    // HTTP mode: exact per-request attribution
    edgeShare = res.CoverageDelta
} else if completedSinceCV >= CoverageInterval {
    // Direct SHM: batch-interval approximation
    delta := GetEdges() - currentEdges
    edgeShare = max(1, delta)
    completedSinceCV = 0
}
if edgeShare > 0 { addOrBoostSeed(item, edgeShare) }
\end{lstlisting}

\subsection{Endpoint-Level Coverage Statistics and Request Prioritization}
\label{sec:endpoint_stats}

For each \texttt{(method, path)} pair, Void maintains an \texttt{EndpointStats} record tracking:
\begin{itemize}
    \item \textbf{NewEdges}: cumulative edges discovered through requests to this endpoint.
    \item \textbf{ReqsSinceEdge}: how many requests have been sent since the last new edge was found on this endpoint.
    \item \textbf{S2xx / S4xx / S5xx}: HTTP status counters for yield estimation.
\end{itemize}

Template selection during the \emph{Mutate} and \emph{Havoc} epochs uses weighted sampling that combines three factors:
\begin{equation}
  w(t) = w_{\text{health}}(t) \cdot w_{\text{dep}}(t) \cdot w_{\text{src}}(t)
  \label{eq:template_weight}
\end{equation}
where $w_{\text{health}}(t)$ penalizes endpoints with many recent 4xx or 5xx errors (indicating structural incompatibility), $w_{\text{dep}}(t)$ boosts endpoints whose producer dependencies have already been satisfied at runtime (e.g., a GET that requires an ID yielded by a prior POST), and $w_{\text{src}}(t)$ gives higher weight to templates derived from grammar templates marked as SSE-enhanced.

\textbf{Coverage stagnation detection.} If no new edge has been discovered for five minutes, Void detects stagnation and resets the \texttt{ReqsSinceEdge} counter for all endpoints that have received fewer than 50 requests, redistributing the sampling weight away from exhausted endpoints toward underexplored ones. Simultaneously, if the global bitmap occupancy exceeds 85\% (indicating rampant hash collisions at Equation~\ref{eq:shm_edge}), Void calls \texttt{SHMCoverageReader.Reset()} to zero the SHM bitmap and restarts accumulation, preventing noise from dominating the novelty signal.

\subsection{Seed Energy and Corpus Evolution}
\label{sec:corpus}

Every request that produces \texttt{edgeShare > 0} is promoted to the seed corpus as a new \texttt{Seed} entry. The energy of a seed encodes its expected future utility for finding new edges:
\begin{equation}
  E(s) = \Delta_{\text{edge}} \cdot \max\!\bigl(1,\; 1 + \log_2(\text{Reqs}(e))\bigr) \cdot \gamma_e
  \label{eq:seed_energy}
\end{equation}
where $\Delta_{\text{edge}}$ is the number of new edges found by $s$, $\text{Reqs}(e)$ is the total number of requests sent to endpoint $e$ at time of discovery, and $\gamma_e = 3.0$ if the endpoint has never produced a new edge before (a \emph{surprise bonus}). The intuition mirrors AFL++'s rare-branch favoring~\cite{afl}: discovering a new edge on an endpoint that has received thousands of requests without finding one is a stronger signal of a novel code path than finding an edge on an untested endpoint.

Seeds are sampled proportionally to their energy for mutation using a \emph{Fenwick tree} (Binary Indexed Tree) probability sampler, enabling $O(\log N)$ weighted selection over a corpus of up to 400 seeds. Corpus minimization runs when the corpus exceeds 500 entries: seeds with energy below 0.3 \emph{and} more than 80 selections without producing new edges are pruned; remaining seeds are sorted by energy and truncated to 400.

\subsection{Campaign Phases and Adaptive Concurrency}
\label{sec:phases}

\textbf{Epoch-based campaign.} Void divides the fuzzing campaign into five sequential phases, each allocated a fraction of the total time budget (Table~\ref{tab:epochs}).

\begin{table}[htbp]
\caption{Void Fuzzing Campaign Epochs}
\label{tab:epochs}
\begin{center}
\begin{tabular}{llrl}
\toprule
\textbf{Epoch} & \textbf{Mode} & \textbf{Budget} & \textbf{Purpose} \\
\midrule
Baseline     & None       & 5\%  & Replay grammar templates sequentially \\
Harvest      & Harvest    & 25\% & Learn dynamic IDs from 2xx responses \\
Deterministic& Mutate     & 25\% & Systematic boundary-value substitution \\
Havoc        & Havoc      & 35\% & Random multi-mutation combinations \\
Splicing     & Havoc      & 10\% & Cross-seed payload recombination \\
\bottomrule
\end{tabular}
\end{center}
\end{table}

At each epoch transition, Void measures the edge discovery rate (edges found per request) achieved during the completed epoch. If the rate falls below $10^{-3}$ edges/request after more than 200 requests, 30\% of that epoch's remaining budget is transferred to the Havoc epoch, which has consistently higher exploration yield for large, multi-structured APIs.

\textbf{Adaptive concurrency.} Void continuously adjusts the goroutine worker count between a configured minimum and maximum, aiming to maximize throughput without saturating the target application. Every second, it computes the request completion rate and error rate over the preceding interval and applies the following heuristic:
\begin{itemize}
    \item If error rate $> 15\%$ or mean response latency $> 3\times$ baseline: reduce concurrency by 2.
    \item If mean latency $> 2\times$ baseline: reduce by 1.
    \item If completion rate $> 75\%$ of current concurrency \emph{and} latency $< 1.3\times$ baseline \emph{and} error rate $< 5\%$: increase by 1.
\end{itemize}
This mirrors congestion-control principles adapted to HTTP workloads, preventing the target server from being overwhelmed while maximizing coverage throughput.

\subsection{Dynamic Value Learning and Stateful Execution}
\label{sec:state}

A fundamental challenge in REST API fuzzing is maintaining producer-consumer state: a POST that creates an object returns a dynamic \texttt{id} that subsequent GET, PUT, and DELETE requests must use. Void addresses this through a \emph{runtime dependency map}: the grammar loader statically identifies all \texttt{restler\_custom\_payload\_uuid4\_suffix} and \texttt{restler\_fuzzable\_*} tokens annotated as expectation-producers in the RESTler grammar and registers their corresponding response-capture regexes. During the Harvest epoch, every successful 2xx response is scanned; captured values (IDs, tokens, anti-forgery headers, session cookies) are stored in a per-execution-context dependency map and substituted into subsequent requests that declare a dependency on them, enabling deep multi-step API state navigation.

\section{Evaluation}
\label{sec:eval}
% ============================================================

\subsection{Research Questions}
\begin{itemize}
    \item \textbf{RQ1}: Does Semantic Source Extraction produce dictionaries that allow the fuzzer to bypass deep backend validation and reach more code paths?
    \item \textbf{RQ2}: Does the greybox coverage-guided loop in Void improve edge coverage and crash discovery compared to the RESTler black-box baseline?
    \item \textbf{RQ3}: What is the practical overhead of the instrumentation and grammar compilation pipeline?
\end{itemize}

\subsection{Experimental Setup}
We evaluate on three open-source .NET REST API applications:

\begin{itemize}
    \item \textbf{nopCommerce}: a mature, open-source e-commerce platform ($\sim$180K lines of C\#, 200+ API endpoints) with extensive Data Annotation and FluentValidation constraints.
    \item \textbf{eShopOnContainers}: Microsoft's reference microservice architecture ($\sim$70K lines C\#, 6 services, 100+ endpoints).
    \item \textbf{mpt-helpdesk}: a custom enterprise helpdesk API ($\sim$25K lines C\#, 60+ endpoints) with complex role-based authorization.
\end{itemize}

For each target, we run two configurations for 24 hours on identical hardware (8-core CPU, 16 GB RAM, no network throttling):
\begin{itemize}
    \item \textbf{Baseline}: RESTler Fuzz mode with default dictionary (no SSE, no coverage feedback).
    \item \textbf{UpsideFuzz}: Full pipeline with SSE-augmented grammar and Void coverage-guided loop.
\end{itemize}

\subsection{Results}

\textbf{RQ1 \& RQ2 -- Coverage and Crashes.}

Across all three targets, UpsideFuzz covers $127\%$--$169\%$ more unique branch edges than the baseline after 24 hours. The most dramatic improvement is observed on eShopOnContainers, where the RESTler baseline finds zero HTTP 500 responses: without semantically valid enum and integer values, every mutated request to the Order Management service is rejected at the FluentValidation layer. UpsideFuzz's SSE pass recovers 12 enum types and 8 numeric ranges from the microservice source trees, enabling the engine to break through validation and discover 3 service crashes.

\textbf{RQ3 -- Pipeline Overhead.}
Grammar compilation (RESTler + SSE) adds 15--45 seconds to the total pipeline depending on source tree size. Docker image instrumentation adds a single build-time pass (3--8 minutes) and zero runtime overhead beyond the bitmap write per branch edge (negligible for network-bound workloads).

\subsection{Case Study: Null Reference Crash in nopCommerce}
Among the 14 HTTP 500 responses found in nopCommerce, 6 are distinct null reference exceptions in the product catalog controller triggered by a specific combination of a valid minimum-length string (exactly 3 characters) and a negative integer value for the \texttt{price} field. Both constraints were recovered by SSE:
\begin{lstlisting}
[MinLength(3)]
public string ProductName { get; set; }

RuleFor(x => x.Price)
    .GreaterThan(0);
\end{lstlisting}
SSE synthesized the boundary values \texttt{"abc"} (length 3) and \texttt{-1} (below the \texttt{GreaterThan(0)} bound). When combined in the same request, the application's price formatting code dereferences a null \texttt{CurrencySettings} object. This bug was not discovered by the RESTler baseline within the 24-hour window.

\section{Discussion}
\label{sec:discussion}
% ============================================================

\textbf{Limitations.}
SSE's regex-based C\# parsing does not handle validation constraints implemented in imperative code (e.g., \texttt{if (value < 0) throw ...}) or computed at runtime from database lookups. Migrating to Roslyn-based AST analysis would increase precision at the cost of requiring a .NET SDK in the Python pipeline; we consider this a worthwhile future direction. Additionally, our evaluation targets open-source .NET applications; results on closed-source or polyglot microservice systems may differ.

\textbf{Applicability.}
While the current implementation targets .NET, the architectural principle of SSE is language-agnostic: similar static passes could recover Jakarta Bean Validation constraints from Java source, Pydantic models from Python, or Joi schemas from TypeScript. Extending UpsideFuzz to these ecosystems is a natural area for future work.

\textbf{Ethical Considerations.}
All experiments were conducted on self-hosted instances of open-source software in isolated Docker environments. No production systems were tested.

% ============================================================
\section{Conclusion}
% ============================================================
We presented UpsideFuzz, a greybox REST API fuzzing framework for .NET that closes the semantic gap between specification-based grammar generation and application-level validation logic. By statically extracting C\# validation constraints and synthesizing boundary-focused dictionary values, UpsideFuzz enables the fuzzer to bypass deep input validation and reach unexplored code paths. Combined with AFL-style edge-coverage feedback collected from SharpFuzz-instrumented .NET processes via shared memory, the Void execution engine evolves a seed corpus that achieves significantly broader coverage than black-box specification-based tools. We hope this work motivates further research into source-aware fuzzing for statically typed, framework-rich server-side ecosystems.
