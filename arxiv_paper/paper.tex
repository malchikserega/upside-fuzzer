\begin{abstract}
% ============================================================
REST APIs are hard to fuzz well because good inputs must be valid at several levels at once. The request must match the HTTP route, the JSON body must be well formed, and the field values must pass the checks used by the application itself. Tools such as RESTler~\cite{restler_icse19} solve the request-sequence problem, but they still use generic values that are often rejected by server-side validation. Standard coverage-guided fuzzers have the opposite problem: they get useful feedback from code coverage, but byte-level mutation breaks HTTP and JSON too easily.

We present \textbf{UpsideFuzzer}, a greybox fuzzing framework for .NET REST services. It has three main parts. First, \textit{Semantic Source Extraction} (SSE) reads C\# validation rules from Data Annotations and FluentValidation and adds better boundary values to RESTler-compatible grammar files. Second, an automated instrumentation pipeline adds SharpFuzz~\cite{sharpfuzz} coverage hooks to Dockerized .NET services. Third, the \textit{Void} runtime sends typed requests from the grammar, tracks new coverage, learns IDs and tokens from successful responses, and uses that information to choose future requests and mutations.

On a 24-hour evaluation over three .NET applications, UpsideFuzzer covers $127\%$ to $169\%$ more unique edges than the RESTler baseline and reaches the first crash much earlier on the tested targets. We also ran a reproducible 20-minute Docker benchmark on four public .NET services. In that benchmark, UpsideFuzzer shows equal or better OpenAPI coverage, much higher throughput, and more HTTP 500-producing method+endpoint pairs overall than the RESTler baseline.
\end{abstract}

\section{Introduction}
% ============================================================
REST APIs are a common attack surface, but they are harder to fuzz than ordinary byte-oriented programs. To reach interesting code, a request usually has to be correct at several levels: the route and method must match, the body must have valid syntax, and the values inside that body must satisfy the rules used by the application. If any of these checks fail, the request is rejected early and the fuzzer learns little about deeper program logic.

Stateful black-box API fuzzers such as RESTler~\cite{restler_icse19} handle the first part of this problem well. Starting from an OpenAPI specification, they infer producer-consumer dependencies and generate valid request sequences. Their weak point is the value space. Default values such as \texttt{"fuzzstring"} or \texttt{0} often fail server-side validation, enum checks, or business rules before the request reaches deeper logic. As Godefroid et al.\ later showed~\cite{restler_fse20}, the values inside API requests are an important part of the search space.

Coverage-guided fuzzers solve a different problem: they use code coverage to guide the search toward new behavior. But most of them mutate raw bytes. For REST APIs, that is usually too destructive. Small byte changes can break the HTTP envelope, the JSON structure, or the path format, so many generated inputs fail before they reach the application code.

UpsideFuzzer combines these two ideas in a simpler way: it keeps RESTler's grammar and request sequencing, but it replaces generic values with better ones taken from the source code and uses coverage feedback to decide what to try next. The key point is that UpsideFuzzer mutates \emph{typed grammar slots}, not arbitrary bytes. Integers stay integers, UUIDs keep their shape, JSON stays parseable, and IDs learned from earlier responses can be reused in later requests. This makes the coverage signal much more useful, because it can be tied to concrete choices such as which endpoint was chosen, which field value was changed, and which runtime dependency was replayed.

\textbf{Contributions.} This paper makes the following contributions:
\begin{itemize}
    \item \textbf{Semantic Source Extraction (SSE):} A static analysis technique for C\# that recovers field-level validation constraints from Data Annotation attributes and FluentValidation rules and synthesizes boundary-focused dictionary values for RESTler's grammar without modifying the RESTler compiler (\S\ref{sec:sse}).
    \item \textbf{Executable Grammar Materialization:} A runtime-oriented grammar export that converts RESTler compiler output into typed templates, dependency descriptors, and dictionary-backed placeholders that can be scheduled, mutated, and attributed by a greybox engine (\S\ref{sec:grammar_model}).
    \item \textbf{Multipart Grammar Injection:} An automated pass that detects \texttt{multipart/form-data} endpoints in OpenAPI specifications and injects syntactically correct, RESTler-native seed request templates, enabling fuzzing of file-upload endpoints that RESTler's compiler cannot handle out-of-the-box (\S\ref{sec:multipart}).
    \item \textbf{Automated IL Instrumentation Pipeline:} A reproducible pipeline that instruments arbitrary .NET Docker images via SharpFuzz without requiring manual harness development, by patching the application Dockerfile at build time (\S\ref{sec:instrumentation}).
    \item \textbf{Void Execution Engine and Feedback Loop:} A highly concurrent Go-based runner that drives the greybox evolutionary loop over RESTler-compiled grammars, combining structured mutation, runtime value learning, endpoint-level prioritization, and shared-memory coverage feedback from the instrumented .NET process (\S\ref{sec:void}).
    \item \textbf{Empirical Evaluation:} A 24-hour comparative study on three .NET applications, plus a reproducible Docker benchmark on four public services, comparing coverage, throughput, and crash discovery against the RESTler black-box baseline (\S\ref{sec:eval}).
\end{itemize}

\section{Background and Related Work}
\label{sec:background}
% ============================================================

\subsection{Coverage-Guided Greybox Fuzzing}
Coverage-guided greybox fuzzing uses program coverage to decide which inputs are worth keeping. In AFL~\cite{afl}, instrumentation adds counters to branch edges, a shared-memory bitmap records which edges were hit, and any input that reaches new coverage is added to the corpus. SharpFuzz~\cite{sharpfuzz} brings the same basic idea to .NET by rewriting compiled IL and inserting edge counters without requiring source-code changes.

\subsection{Specification-Based API Fuzzing}
RESTler~\cite{restler_icse19} is a stateful REST API fuzzer built around OpenAPI specifications. It analyzes producer-consumer dependencies between operations, then generates request sequences that follow those dependencies. Its grammar separates \emph{static} tokens copied from the specification from \emph{fuzzable} tokens that are filled with values at runtime. This works well for request sequencing and basic structure, but the default value dictionaries are small and generic, so domain-specific values usually have to be added by hand.

\subsection{Intelligent API Data Fuzzing}
Godefroid et al.~\cite{restler_fse20} later focused on the values inside REST requests, not just the request sequence. They explored schema-level body mutations such as type substitution, field deletion, and value replication, and also studied two ways to get better concrete values: using examples from the specification and learning values from earlier responses. Their results show that generic random values are weak for structured JSON and that better values improve bug discovery. UpsideFuzzer follows the same general direction, but gets these values from .NET source code rather than only from the specification or earlier responses.

\subsection{Other Related Tools}
EvoMaster~\cite{evomaster} is a white-box REST API testing tool for JVM services. It uses evolutionary search and runtime instrumentation, but it targets a different ecosystem and does not recover validation rules from source annotations. WuppieFuzz~\cite{wuppiefuzz} is a newer framework built on LibAFL that supports several API fuzzing modes, but it also does not extract validation semantics from application source code. Dredd~\cite{dredd}, APIFuzzer~\cite{apifuzzer}, and schemathesis~\cite{schemathesis} generate tests directly from API specifications and do not use code coverage. In short, existing tools usually give you either good request structure or good coverage guidance; UpsideFuzzer is meant to combine those two with source-derived validation values for .NET services.

\section{System Architecture}
\label{sec:arch}
% ============================================================

UpsideFuzzer has four main components and runs in two phases: an offline \emph{preparation phase} and an online \emph{fuzzing phase}. Figure~\ref{fig:architecture} shows the full pipeline.

\textbf{Preparation phase.} Given a target .NET application repository and an OpenAPI specification, the user runs:
\begin{enumerate}
    \item \texttt{fuzz-prep-multi.py}: instruments the application image (Section~\ref{sec:instrumentation});
    \item \texttt{compile-grammar.sh}: invokes the RESTler compiler to produce a raw grammar, then calls the SSE enhancer (Section~\ref{sec:sse}) to augment it.
\end{enumerate}

\textbf{Fuzzing phase.} The Void runtime (Section~\ref{sec:void}) runs next to the instrumented application container. It sends requests from the grammar, reads coverage from the target, and updates its seed corpus over time.

\subsection{Grammar Artifacts and Runtime Input Model}
\label{sec:grammar_model}
The online fuzzer does not read raw OpenAPI JSON directly. Instead, \texttt{compile-grammar.sh} produces three files that Void uses at runtime:
\begin{enumerate}
    \item \textbf{\texttt{grammar.py}}: the original RESTler grammar, preserved as the canonical compiler output;
    \item \textbf{\texttt{dict.json}}: the mutation dictionary, augmented by SSE with domain-specific boundary values, enum members, and format-aware examples;
    \item \textbf{\texttt{templates.export.json}}: a normalized runtime view of the grammar in which every RESTler \texttt{Request} object is exported into a compact, language-agnostic representation that Void can load directly.
\end{enumerate}

Each exported template corresponds to one OpenAPI operation. It contains a \texttt{request\_id}, a list of \texttt{segments}, and \texttt{reads}/\texttt{writes} dependency annotations recovered by RESTler. A segment can be one of three kinds:
\begin{itemize}
    \item \textbf{static}: immutable bytes copied verbatim from the grammar, such as HTTP verbs, route delimiters, header names, or fixed query keys;
    \item \textbf{fuzzable}: a typed placeholder (e.g., \texttt{string}, \texttt{int}, \texttt{uuid}, \texttt{datetime}) whose runtime value is chosen from \texttt{dict.json}, optionally mutated further by Void;
    \item \textbf{custom\_payload}: a dependency-bearing placeholder whose value must be learned dynamically from earlier successful responses (e.g., a server-generated resource identifier).
\end{itemize}

This format matters for two reasons. First, requests stay structurally valid, because mutation only changes typed slots instead of editing random bytes in a serialized HTTP message. Second, the \texttt{reads}/\texttt{writes} annotations give Void enough information to handle state, for example when one request creates an ID that another request must reuse later. In practice, the grammar becomes an executable input model for valid and stateful HTTP requests.

\subsection{Lowering an Endpoint into a Runtime Template}
\label{sec:endpoint_lowering}
The endpoint-to-grammar lowering step is where the OpenAPI description turns into something the greybox runtime can use. A single operation such as
\begin{lstlisting}
POST /api/orders/{orderId}/lines?api-version=1.0
Content-Type: application/json

{"sku": "...", "quantity": 1}
\end{lstlisting}
is exported into a template that keeps the HTTP skeleton but exposes only the useful choice points:
\begin{lstlisting}
request_id: post_order_line
segments:
  - static: "POST /api/orders/"
  - custom_payload: orderId
  - static: "/lines?api-version=1.0 HTTP/1.1\r\n..."
  - static: "{\"sku\":"
  - fuzzable(string): sku
  - static: ",\"quantity\":"
  - fuzzable(int): quantity
  - static: "}"
reads:  ["orderId"]
writes: []
\end{lstlisting}
This makes the control points explicit. Path parameters that depend on earlier requests become \texttt{custom\_payload} slots, fixed query values stay \texttt{static}, and body fields become typed \texttt{fuzzable} slots. Void does not try to discover the route shape by byte mutation. It inherits the route and framing from the template and only searches over the values inserted into the slots. If an earlier response produced an order identifier, the \texttt{orderId} slot is filled from the runtime store; otherwise Void falls back to the dictionary and then mutates the value in a type-aware way.

This template form also makes later coverage attribution possible. Each rendered request keeps its \texttt{request\_id}, HTTP method, normalized path, and mutation label, so a later edge gain can be tied back to a concrete operation and mutation choice.

\section{Automated Instrumentation Pipeline}
\label{sec:instrumentation}
% ============================================================

To collect edge coverage without writing a custom harness, UpsideFuzzer adds SharpFuzz instrumentation during the Docker build. The preparation script \texttt{fuzz-prep-multi.py} does the following:

\begin{enumerate}
    \item \textbf{Clone and patch the build.} The script clones the target repository and adds the \texttt{SharpFuzz.Instrumentation} package to the Docker build.
    \item \textbf{Rewrite IL.} During the image build, SharpFuzz rewrites the target \texttt{.dll} files and inserts an edge counter before each branch target:
        \begin{equation}
          \text{bitmap}[(\text{prev\_loc} \oplus \text{cur\_loc}) \gg 1]\ \text{+=}\ 1
          \label{eq:shm}
        \end{equation}
        where \texttt{prev\_loc} and \texttt{cur\_loc} are random 16-bit identifiers for basic blocks, following the AFL shared-memory protocol~\cite{afl}. This produces a 65,536-byte bitmap in shared memory.
    \item \textbf{Expose coverage over HTTP when needed.} The script can patch \texttt{Program.cs} to expose the shared-memory bitmap through HTTP, which is useful in Docker setups where direct file sharing is inconvenient.
    \item \textbf{Update Docker Compose.} The compose file is updated so the coverage endpoint and shared-memory region are available at runtime.
\end{enumerate}

In practice, this adds only one extra Docker build cycle and does not require any manual harness code.

\section{Semantic Source Extraction}
\label{sec:sse}
% ============================================================

\begin{figure}[htbp]
\centerline{\includegraphics[width=\linewidth]{sse.pdf}}
\caption{Semantic Source-Aware Grammar Enhancement Pipeline.}
\label{fig:sse}
\end{figure}

\subsection{Motivation}
RESTler knows how to build valid request sequences, but its default values are often too generic to pass application-level validation. For example, if a backend requires \texttt{[StringLength(8, MinimumLength=4)]}, a value such as \texttt{"fuzzstring"} may be rejected immediately. In that case the request never reaches the deeper logic behind the validator. Semantic Source Extraction (SSE) tries to fix this by filling the dictionary with better boundary values taken from the application's own validation rules.

\subsection{Pipeline Overview}
SSE has two parts. First, it reads the OpenAPI specification and collects constraints such as \texttt{minLength}, \texttt{maxLength}, \texttt{minimum}, \texttt{maximum}, \texttt{pattern}, and \texttt{enum}. Second, it scans the C\# source tree to recover constraints that are missing from the specification or more precise than what the specification says.

\subsection{OpenAPI Constraint Extraction}
The \texttt{OpenAPIExtractor} walks through the Swagger schema, resolves \texttt{\$ref} links, and expands \texttt{allOf}/\texttt{oneOf}/\texttt{anyOf} nodes. For each final property, it builds a \texttt{FieldHint} record containing the field type, format, declared constraints, and any inline \texttt{example} or \texttt{default} value. If a field is a binary string in a \texttt{multipart/form-data} operation, it is marked for the multipart injection pass (Section~\ref{sec:multipart}).

\subsection{C\# Source Code Constraint Extraction}
\label{sec:src_extract}
The \texttt{SourceExtractor} runs a regex-based pass over all \texttt{.cs} files in the target tree. A full Roslyn-based analysis would be more precise, but regex is much lighter and works well for the common validation patterns used in .NET projects.

\textbf{Data Annotation Attributes.} The extractor identifies attribute blocks preceding property or parameter declarations and parses the following attributes (case-insensitive):
\begin{itemize}
    \item \texttt{[StringLength(N)]} and \texttt{[StringLength(N, MinimumLength=M)]}: sets $\textit{max\_length} = N$, $\textit{min\_length} = M$.
    \item \texttt{[MaxLength(N)]}, \texttt{[MinLength(M)]}: sets the corresponding bound.
    \item \texttt{[Range(lo, hi)]}: sets $\textit{minimum} = lo$, $\textit{maximum} = hi$.
    \item \texttt{[RegularExpression("pattern")]}: stores the regex pattern.
    \item \texttt{[Required]}: marks the field as non-nullable.
    \item \texttt{[EmailAddress]}, \texttt{[Url]}: activates format-specific value generators.
\end{itemize}

\textbf{FluentValidation Rules.} For validators that extend \texttt{AbstractValidator<T>}, the extractor scans \texttt{RuleFor(...)} chains and recognizes the following rule methods:
\begin{itemize}
    \item \texttt{.MaximumLength(N)}, \texttt{.MinimumLength(M)}, \texttt{.Length(M,N)}: string length bounds.
    \item \texttt{.InclusiveBetween(lo, hi)}, \texttt{.ExclusiveBetween(lo, hi)}: numeric bounds.
    \item \texttt{.GreaterThan(v)}, \texttt{.LessThan(v)}: one-sided numeric bounds.
    \item \texttt{.Matches("pattern")}: regex pattern.
    \item \texttt{.NotEmpty()}, \texttt{.NotNull()}: required-field marking.
    \item \texttt{.EmailAddress()}, \texttt{.Must(IsUrl)}: format validators.
\end{itemize}
When the same constraint appears in both the specification and the source code, SSE keeps the tighter one.

\textbf{Enum Resolution.} For each property or parameter whose type resolves to a C\# \texttt{enum}, the extractor locates the enum declaration in the source tree and parses all symbolic members, including their optional explicit integer assignments. Both the symbolic name and its integer equivalent are added to the dictionary, following the observation in~\cite{restler_fse20} that enum-constrained fields require exact value matches to progress past validation.

\subsection{Boundary Value Synthesis}
Given a \texttt{FieldHint}, SSE builds a small set of boundary-focused test values. For numeric fields it uses $\{lo-1, lo, hi, hi+1\}$. For string-length constraints it uses values around the minimum and maximum lengths. For regex constraints it adds one matching and one non-matching example. These values are inserted into the RESTler dictionary under several name variants such as camelCase, PascalCase, and lowercase.

An important point is that SSE does not replace RESTler's grammar or compiler. It only adds better values to the dictionary and, when needed, appends extra seed templates.

\subsection{From Field Hints to Grammar Augmentation}
\label{sec:hint_to_grammar}
The SSE output is merged back into the grammar in a format RESTler already understands. UpsideFuzzer does not introduce a new request DSL. It writes into the same dictionary namespaces that RESTler already uses, such as \texttt{restler\_fuzzable\_string}, \texttt{restler\_fuzzable\_int}, and \texttt{restler\_custom\_payload}. The merge follows two simple rules:
\begin{enumerate}
    \item \textbf{Preserve type compatibility.} A value recovered for an integer-constrained field is inserted into integer-typed buckets; enum names and regex examples are inserted into string-typed buckets; dynamic identifiers are inserted into custom-payload buckets so they can later be substituted into dependency-bearing grammar positions.
    \item \textbf{Preserve grammar structure.} Existing RESTler request templates remain unchanged unless a feature is unsupported by the compiler itself (e.g., multipart endpoints). Thus, SSE changes the \emph{value space} explored by the grammar, not the state machine over which RESTler already reasons.
\end{enumerate}

This matters for the evaluation. The request sequence model still comes from RESTler; UpsideFuzzer mainly changes the value space and then uses coverage to decide which parts of that space deserve more effort.

% ============================================================
\section{Multipart Grammar Injection}
\label{sec:multipart}
% ============================================================
RESTler's compiler handles \texttt{multipart/form-data} poorly: it often emits one fuzzable string for the whole body, which is not valid multipart syntax. UpsideFuzzer detects multipart operations in the OpenAPI specification and generates corrected RESTler-style request templates for them. These templates include the MIME boundary, the correct \texttt{Content-Disposition} headers, and a binary payload stub (\texttt{fuzz.bin}) for file fields. They are appended directly to \texttt{grammar.py}, so Void can fuzz file-upload endpoints without manual setup.

\section{The Void Execution Engine}
\label{sec:void}
% ============================================================

\subsection{Architecture Overview}
Void is a multi-goroutine HTTP fuzzing engine implemented in Go ($\sim$3,500 lines). Its overall structure follows a producer-consumer pipeline: a \emph{dispatcher goroutine} generates \texttt{WorkItem} structs (each encoding an HTTP method, path, body, headers, mutation name, and seed index), enqueues them into a bounded channel, and a fixed \emph{worker pool} of goroutines concurrently dispatches them over HTTP. Completed \texttt{SendResult} structs are returned via a result channel to a single \emph{result handler} that updates global state without locks.

\subsection{Coverage-Guided Feedback Loop}
\label{sec:feedback_loop}
The main idea behind Void is simple: send a request, check if it reached new code, and if it did, remember what worked and do more of it. The difference from traditional byte-level fuzzers like AFL is that Void mutates \emph{typed grammar slots} instead of random bytes, so it always knows which endpoint, which field, and which kind of mutation led to new coverage.

\subsubsection{Loop Overview}
Each iteration of the main loop performs the following steps:
\begin{enumerate}
    \item \textbf{Pick a seed.} Choose one of the previously successful requests from the corpus. Seeds that found more coverage get picked more often.
    \item \textbf{Build a request.} Take the grammar template, fill in the blanks: copy static parts, plug in learned IDs for \texttt{custom\_payload} slots, pick or mutate values for \texttt{fuzzable} slots.
    \item \textbf{HTTP execution.} Send the rendered request. Record the response status, body, latency, and any \texttt{X-Coverage-Delta} response header injected by the .NET coverage middleware.
    \item \textbf{Coverage measurement.} If the response contains a per-request coverage delta (HTTP mode), use it directly. Otherwise, after every $N$ completed requests, poll the shared-memory bitmap and compute the global edge delta.
    \item \textbf{Update state.} If new edges were found: save this request as a new seed, give it more weight so it gets picked again, and note which mutation type worked. If nothing new: bump a stall counter. After enough stalls, Void tries harder mutations.
\end{enumerate}

\subsubsection{Pseudocode}
Algorithm~\ref{alg:feedback} shows the pseudocode. The three key decisions are: (a)~which seed to pick (weighted by past success), (b)~how to read coverage (per-request header when available, or periodic bitmap check), and (c)~how to reward successful mutations.

\begin{algorithm}[t]
\caption{Coverage-Guided Feedback Loop}
\label{alg:feedback}
\begin{algorithmic}[1]
\REQUIRE Templates $\mathcal{T}$, dictionary $\mathcal{D}$, store $\mathcal{R}$, budget $B$
\STATE $\mathcal{C} \leftarrow$ baseline rendering of all templates
\STATE edges $\leftarrow 0$; stall $\leftarrow 0$; done $\leftarrow 0$
\WHILE{elapsed $< B$}
    \STATE epoch $\leftarrow$ currentEpoch(elapsed, $B$)
    \IF{epoch is Mutate/Havoc and $|\mathcal{C}| > 0$}
        \STATE $i \leftarrow$ FenwickPick($\mathcal{C}$)
        \STATE $\mathcal{C}[i]$.energy $\leftarrow \mathcal{C}[i]$.energy $\times\, 0.995$
    \ELSE
        \STATE $t \leftarrow$ weightedTemplatePick($\mathcal{T}$)
    \ENDIF
    \STATE req $\leftarrow$ render($t$, epoch.mode, $\mathcal{D}$, $\mathcal{R}$)
    \STATE resp $\leftarrow$ sendHTTP(req); done $\leftarrow$ done $+ 1$
    \IF{resp.coverageDelta $> 0$}
        \STATE $\delta \leftarrow$ resp.coverageDelta
    \ELSIF{done mod interval $= 0$}
        \STATE $\delta \leftarrow$ readSHM() $-$ edges
    \ELSE
        \STATE $\delta \leftarrow 0$
    \ENDIF
    \STATE edges $\leftarrow$ edges $+ \delta$
    \IF{$\delta > 0$}
        \STATE stall $\leftarrow 0$
        \STATE surprise $\leftarrow (1 + \log_2$ ep.reqs$) \cdot \gamma_e$
        \STATE addSeed($\mathcal{C}$, req, $\delta \cdot$ surprise)
        \STATE boostParent($\mathcal{C}[i]$, $\delta \times 5$)
        \STATE recordCategoryHit(req.label)
    \ELSE
        \STATE stall $\leftarrow$ stall $+ 1$
    \ENDIF
    \STATE updateMutWeights()
    \STATE learnValues(resp, $\mathcal{R}$)
    \IF{$|\mathcal{C}| > 500$}
        \STATE minimizeCorpus($\mathcal{C}$)
    \ENDIF
\ENDWHILE
\end{algorithmic}
\end{algorithm}

\subsubsection{Scheduling Priority}
The chance of picking a seed-template pair depends on two things:
\begin{equation}
  \text{pick\_chance}(s, t) \;\propto\; \text{seed\_energy}(s) \;\times\; \text{template\_weight}(t)
  \label{eq:loop_priority}
\end{equation}
Seeds that found more coverage have higher energy, so they get picked more often. Templates for endpoints that keep failing lose weight. Every time a seed is picked, its energy drops by 0.5\%, so no single seed can dominate forever.

\subsection{From Endpoint Parameters to Coverage-Directed Mutation}
\label{sec:param_to_cov}
The key implementation detail is how one endpoint instance turns into a coverage gain and then into a new mutation choice. In the current Go runtime, that happens in four stages.

\textbf{Stage 1: fill the template.} The renderer walks through the template from left to right. \texttt{static} segments are copied as-is. \texttt{custom\_payload} segments first try to use IDs or tokens learned from earlier responses; if none are available, Void falls back to dictionary values. \texttt{fuzzable} segments are filled from typed defaults and may then be mutated. JSON bodies and ID-like path segments may also receive extra structured mutations depending on the current epoch.

\textbf{Stage 2: execute and measure.} The rendered request is sent together with its metadata: \texttt{request\_id}, method, normalized path, mutation label, and seed index. If the target returns an \texttt{X-Coverage-Delta} header, Void gets an exact per-request edge delta. Otherwise it falls back to periodic SHM polling, which gives a noisier but still useful signal.

\textbf{Stage 3: update endpoint and mutation statistics.} Once the result arrives, Void updates the endpoint record keyed by normalized \texttt{(method, path)} and the mutation record keyed by \texttt{MutationName}. Requests always increase the request counter. New edges increase both endpoint and mutation scores. In code, the core update looks like this:
\begin{lstlisting}
item := render(template, seed)
resp, delta := execute(item)
ep.Reqs++
mut.Attempts++
if delta > 0 {
    ep.NewEdges += delta
    mut.NewEdges += delta
    recordMutationCategoryHit(item.Label)
    addOrBoostSeed(item, delta)
}
\end{lstlisting}

\textbf{Stage 4: change future choices.} The result updates three things at once. First, requests that find new edges become seeds with higher energy, so they get picked more often. Second, endpoints that keep failing lose weight (and with \texttt{--skip-endpoint-on-500}, a method+endpoint pair is removed after the first HTTP~500). Third, mutation categories that find new edges get their weight bumped:
\begin{equation}
  \text{category\_weight} = 1 + 4 \times \frac{\text{hits}}{\text{attempts}}
  \label{eq:mutcat_weight}
\end{equation}
In practice, a mutation family that keeps finding new edges can become up to $5\times$ more likely to be selected than one that never does.

This is the full endpoint-to-coverage-to-mutation chain. A useful request does not just increase a counter in a bitmap. It changes which seeds, endpoints, and mutation families are more likely to be used next.

\subsection{Adaptive Mutation Scheduling (MOpt)}
\label{sec:mopt}
Void organizes string mutation payloads into 15 categories corresponding to common vulnerability classes: boundary, overflow, SQL injection, XSS, command injection, path traversal, SSRF, SSTI, CRLF injection, open redirect, Log4Shell, NoSQLi, LDAP injection, XXE, and Unicode tricks. Each category has a runtime weight that starts at a class-dependent baseline (typically 1.0--1.5) and is updated based on how often it discovers new edges.

Algorithm~\ref{alg:mopt} shows the selection and weight update logic. The design follows MOpt~\cite{mopt}: categories that improve coverage become more likely to be selected in the future. Numbers and dates have separate type-aware mutators that do not use the category system.

\begin{algorithm}[t]
\caption{MOpt-Style Adaptive Mutation Selection}
\label{alg:mopt}
\begin{algorithmic}[1]
\REQUIRE Categories $\{c_1, \ldots, c_K\}$ with weights $w_k$, payloads $P_k$
\STATE \textbf{// Select category (weighted random):}
\STATE Draw $r \sim \text{Uniform}(0, \sum w_k)$
\STATE Pick $c_j$ such that $\sum_{k=1}^{j-1} w_k < r \le \sum_{k=1}^{j} w_k$
\STATE Draw payload $p \sim \text{Uniform}(P_j)$
\STATE $c_j$.Attempts $\leftarrow c_j$.Attempts $+ 1$
\STATE \textbf{return} $p$, category label ``mcat\_$c_j$.name''
\STATE
\STATE \textbf{// On coverage gain (called from feedback loop):}
\FORALL{$c_k$ where label contains ``mcat\_$c_k$.name''}
    \STATE $c_k$.Hits $\leftarrow c_k$.Hits $+ 1$
\ENDFOR
\STATE
\STATE \textbf{// Periodic weight recalculation:}
\FORALL{$c_k$ with Attempts $> 0$}
    \STATE $w_k \leftarrow 1.0 + 4.0 \times c_k$.Hits / $c_k$.Attempts
\ENDFOR
\end{algorithmic}
\end{algorithm}

\subsection{Structured Mutation Operators}
\label{sec:mut_operators}
Void mutates requests in a grammar-aware way. For scalar slots it uses type-specific operators, so integers stay integer-shaped, dates stay date-shaped, and UUIDs stay UUID-shaped. For string fields it uses groups of payloads aimed at common bug classes such as boundary violations, SQL injection, XSS, command injection, path traversal, SSRF, and CRLF. Categories that lead to new edges are given higher weight over time.

For larger bodies, Void uses \emph{structured body havoc} instead of blind text corruption. JSON bodies may lose fields, duplicate fields, change types, insert nulls, or combine nested fragments, but they are kept parseable as JSON. Path mutation is limited to segments that look like resource identifiers, so the general route shape stays valid. During the splicing phase, Void also combines parts of already useful seeds. This is more aggressive than simple dictionary substitution, but still much safer than byte-level fuzzing for web APIs.

\subsection{SharpFuzz Instrumentation and Coverage Transport}
\label{sec:coverage_transport}

\textbf{SHM bitmap layout.} SharpFuzz inserts a counter on each branch edge in the compiled code. When execution crosses an edge between two blocks, it XORs the block identifiers and uses the result as an index into a 65,536-byte shared-memory bitmap --- the same approach as AFL~\cite{afl}. Each byte in the bitmap counts how many times that particular edge was hit.

\textbf{Two coverage transport modes.} The instrumented .NET process exposes this bitmap in two modes:

\begin{enumerate}
    \item \textbf{Direct SHM mode}: Void opens the shared-memory region under \texttt{/dev/shm}. It keeps a local \texttt{seen[65536]} array and, on each poll, counts bytes that are non-zero in SHM but zero in \texttt{seen[]}:
\begin{lstlisting}
for i, b := range shmBuf {
    if b != 0 && seen[i] == 0 {
        seen[i] = 1; edges++ } }
\end{lstlisting}
    The bitmap is not reset after every request in this mode. Void only clears it when occupancy becomes too high and the novelty signal becomes noisy.
    \item \textbf{HTTP coverage mode}: The patched ASP.NET Core application exposes \texttt{/shm/create}, \texttt{/shm/coverage}, and \texttt{/shm/reset}. Void resets coverage before the request and reads it after the request, which gives reliable per-request attribution. This mode is useful when direct file sharing is not available.
\end{enumerate}

\subsection{Attribution Accuracy: HTTP Mode vs.\ Direct SHM Mode}
\label{sec:attribution}

The two transport modes differ in how precisely they can attribute edge discovery to individual requests under concurrency.

\textbf{HTTP mode (exact attribution).} The ASP.NET middleware brackets one request with a \texttt{ResetCoverage()} before controller execution and a bitmap count immediately before the response is returned. The resulting \texttt{X-Coverage-Delta} header therefore corresponds to that exact request, even when many workers are active.

\textbf{Direct SHM mode (approximate attribution).} Concurrent requests share one bitmap, so Void can observe only the net edge increase between polling points. It therefore credits the interval gain to the most recently completed request. This is noisier at per-request granularity, but in practice still provides a useful signal for endpoint-level scheduling and seed promotion over long campaigns.

HTTP mode is preferred whenever middleware injection succeeds; direct SHM remains the fallback for third-party Docker deployments where only shared-memory transport is available.

\subsection{Endpoint-Level Coverage Statistics and Request Prioritization}
\label{sec:endpoint_stats}

For each \texttt{(method, path)} pair, Void maintains an \texttt{EndpointStats} record tracking:
\begin{itemize}
    \item \textbf{NewEdges}: cumulative edges discovered through requests to this endpoint.
    \item \textbf{ReqsSinceEdge}: how many requests have been sent since the last new edge was found on this endpoint.
    \item \textbf{S2xx / S4xx / S5xx}: HTTP status counters for yield estimation.
\end{itemize}

Template selection during the \emph{Mutate} and \emph{Havoc} epochs uses weighted sampling that combines three factors:
\begin{equation}
  \text{template\_weight}(t) = \text{health}(t) \times \text{deps\_ready}(t) \times \text{sse\_boost}(t)
  \label{eq:template_weight}
\end{equation}
Here, \texttt{health} is lower for endpoints with many recent errors, \texttt{deps\_ready} is higher when the endpoint's dependencies (like IDs from other requests) are already available, and \texttt{sse\_boost} gives extra weight to endpoints whose grammar was enhanced by SSE.

\textbf{Coverage stagnation detection.} If no new edge appears for several minutes, Void treats the current search as stale and gives more attention to endpoints that have not been explored enough. If the bitmap becomes too full, it is reset so hash collisions do not hide new behavior.

\subsection{Seed Energy and Corpus Evolution}
\label{sec:corpus}

Every request that finds new edges is saved into the seed corpus. Its energy (priority for future selection) is calculated as:
\begin{equation}
  \text{energy} = \text{new\_edges} \;\times\; (1 + \log_2 \text{endpoint\_reqs}) \;\times\; \text{bonus}
  \label{eq:seed_energy}
\end{equation}
The idea is simple: finding new code on an endpoint that has already received many requests is a bigger surprise than finding it on a fresh endpoint. The \texttt{bonus} is $3.0$ when the endpoint had never produced a new edge before. In plain terms, hard-won discoveries get more energy.

Seeds are sampled in proportion to their energy using a \emph{Fenwick tree} sampler. When the corpus grows too large, low-value seeds that have been retried many times without finding new edges are pruned.

\textbf{Epoch-based campaign.} Void divides a run into five phases (Table~\ref{tab:epochs}).

At each phase transition, Void checks how many new edges the previous phase found. If progress becomes too slow, part of the remaining time is moved to the Havoc phase, which is usually better at broad exploration.

\textbf{Adaptive concurrency.} Void continuously adjusts the goroutine worker count between a configured minimum and maximum, increasing it when completion rate rises without latency or error inflation and decreasing it when latency or error rate spikes. This mirrors congestion-control principles adapted to HTTP workloads, preventing the target server from being overwhelmed while maximizing coverage throughput.

\subsection{Dynamic Value Learning and Stateful Execution}
\label{sec:state}

A common problem in API fuzzing is state. A POST may create an object and return an \texttt{id}, and later GET, PUT, and DELETE requests must reuse that value. Void handles this with a runtime dependency map. During the Harvest phase, successful 2xx responses are scanned for values such as IDs, tokens, anti-forgery fields, and session cookies. Those values are stored and later replayed into requests that depend on them.

Void learns from both requests and responses. It uses the request shape to understand which values belong to which resources, and it uses response headers and bodies to recover concrete runtime values. When a later template needs a \texttt{custom\_payload} value, the renderer first tries these learned values before falling back to the static dictionary.

\subsection{Identity, Session, and Form-State Handling}
\label{sec:auth_state}
Many real APIs need more than one kind of runtime state. Void therefore supports multiple authentication identities, token and cookie refresh, and automatic handling of anti-forgery tokens for form-style endpoints. This keeps the fuzzing loop from getting stuck in repeated authorization failures when the interesting code is only reachable after login or through protected workflows.

\subsection{Research Questions}
\begin{itemize}
    \item \textbf{RQ1}: Does Semantic Source Extraction produce dictionaries that allow the fuzzer to bypass deep backend validation and reach more code paths?
    \item \textbf{RQ2}: Does the greybox coverage-guided loop in Void improve edge coverage and crash discovery compared to the RESTler black-box baseline?
    \item \textbf{RQ3}: What is the practical overhead of the instrumentation and grammar compilation pipeline?
\end{itemize}

\subsection{Experimental Setup}
We evaluate on three .NET REST API applications: two open-source systems and one internal enterprise API.

\begin{itemize}

\begin{itemize}

\subsection{Case Study: Null Reference Crash in nopCommerce}
Among the 14 HTTP 500 responses found in nopCommerce, 6 are distinct null reference exceptions in the product catalog controller triggered by a specific combination of a valid minimum-length string (exactly 3 characters) and a negative integer value for the \texttt{price} field. Both constraints were recovered by SSE:
\begin{lstlisting}
[MinLength(3)]
public string ProductName { get; set; }

RuleFor(x => x.Price)
    .GreaterThan(0);
\end{lstlisting}
SSE synthesized the boundary values \texttt{"abc"} (length 3) and \texttt{-1} (below the \texttt{GreaterThan(0)} bound). When combined in the same request, the application's price formatting code dereferences a null \texttt{CurrencySettings} object. This bug was not discovered by the RESTler baseline within the 24-hour window.

\section{Discussion}
\label{sec:discussion}
% ============================================================

\textbf{Limits of the current implementation.}
SSE uses regex-based parsing of C\# files, so it works best for common validation patterns such as Data Annotations and FluentValidation chains. It does not fully cover checks written in imperative code, values loaded from a database, or rules that are built dynamically at runtime. A Roslyn-based parser would likely improve precision, but it would also make the preparation pipeline heavier.

\textbf{Threats to validity.}
Our measurements use more than one metric, and those metrics should not be mixed. The 24-hour study focuses on code coverage and crash discovery, while the Docker benchmark also reports OpenAPI coverage and endpoint-normalized HTTP 500 counts. In addition, some Docker targets required prepared benchmark artifacts such as sanitized specifications, fixed version parameters, or injected authentication tokens. These steps were applied equally to the compared tools, but they still mean that the benchmark measures the prepared target configuration rather than an untouched public deployment. Finally, one target in the 24-hour study is an internal enterprise API, so that part of the evaluation is less reproducible than the public Docker benchmark.

\textbf{Where the approach should transfer.}
The current implementation is built for .NET, but the main idea is not tied to C\#. The same general approach could be applied in other ecosystems by extracting validation rules from their native frameworks, for example Jakarta Bean Validation in Java, Pydantic in Python, or Joi schemas in TypeScript.

\textbf{Ethics.}
All experiments were run on self-hosted test instances in isolated Docker environments. No production systems or third-party services were fuzzed.

% ============================================================
\section{Conclusion}
% ============================================================
UpsideFuzzer is a greybox REST API fuzzer for .NET that keeps RESTler's grammar structure, adds better values from C\# validation code, and uses coverage to guide what to try next. In our evaluation, this combination reached more code and found failures faster than the RESTler baseline. More broadly, the results suggest that API fuzzing improves when request structure, source-derived semantics, and coverage feedback are used together instead of in isolation.
